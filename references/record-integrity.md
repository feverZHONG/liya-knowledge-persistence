## 决策记录（拍板）规范

拍板/决策类记录落盘规范（吸收自 dsh 团队 Agent Notes 制度，`<档案目录>/dsh-reference/.agents/notes/README.md`）：

1. **记拍板 = 原话不加解读**
2. **必记「否掉了什么」** — 方案 + 落选原因（不记被击败的方案=邀请反复争论）
3. **决策被取代用新记录** — 不回头改写旧决策；新记录注明「取代 xxx（日期）」互链
4. **文件内骨架**：`## 拍板（原话）` / `## 否掉了什么（方案+原因）` / `## 影响/后果`
5. **归档冻结** — 落地后不再编辑正文（事实修正除外），过期决策移归档目录标日期

### D18 · 级联登记：新事实推翻旧前提时，去改那处文件（2026-09-10 V4 Pro

18. **级联登记：新事实推翻旧前提时，去改那处文件（2026-09-10 V4 Pro 下线实例）** — 一条事件的结论若改写了**别处既有台账的前提**，不能只在事件条目里写完就收工。步骤：① grep 依赖该事实的地方（订阅/成本对位表、模型档位速查、报价与待购笔记、ENV.md 类环境快照）；② 在被影响文件里加一段「YYYY-MM-DD 更新 · <事件>」，写清**影响点**并回指事件条目。实例：V4 Pro 下线 → `<记忆目录>/ai-subscription-experience.md` 里「MiMo 订阅 ≈ DS 按量 2.3~4.7 倍量（对位 v4-flash/v4-pro）」的**双档**前提失效，需按 Flash 单档重算。**不级联 = 那处文件以后拿着过期前提继续用**，比没记更糟——错的前提比缺的信息更容易被信任


### D18b · 反向同样成立：旧结论会随上游机制静默失效

- **反向同样成立：旧结论会随上游机制静默失效**——档案里最脆的一类是「调查过、决定不做」：「X 不支持 Y，所以只能 Z」。上游加一个新机制，整段结论连同它的「不值得／是大工程」一起作废，而下个会话只读到旧结论（实例：某平台接入档案写「接非官方协议端＝源码级开发、容器重建丢补丁」，上游后来加了插件注册机制＝零改核心、跟仓库走，那份「不上」的结论当场失效）。两条规矩：① 写结论时**把前提写在结论旁边**（「因为 X 不支持 Y，所以…」）——前提一变结论自己失效，一眼看得出；② 引用旧档下判断前先跑一次**最便宜的机制探测**（源码里有没有那个目录／命令、`--help`、官方文档路径）再复述，别把旧结论当事实往下传；③ 复核后**就地改掉那句结论**并补一节增量，别在下面叠「UPDATE：其实…」——旧结论还在，下一个会话照样先读到它。


### D19 · 登记「事件+推断」分层落笔（2026-09-10 合金弹头清场线实例）

19. **登记「事件+推断」分层落笔（2026-09-10 合金弹头清场线实例）** — 一条热点被要求登记时，别把可查事实和网上的结论揉成一团。四栏分开：① **事实层**＝可查证事件，每条带日期+来源+状态；② **推断层**＝用户/社区的判断，单独标 **【用户推断】**，绝不写进事实层；③ **原话栏**＝照抄不加工（缩写保留**原形**，如 fwsbk——不展开、不解释）；④ **待核栏**＝查不到的写「⚠️ 待核」+ 写清「验证点是什么」（例：还有哪家平台会跟进下架）。事件成立但精确日期只过到转载群的，写「✅ 事件成立，精确日期待核」——**为好看抹平不确定度是记账事故**。证据图落法：图不进 git → `downloads/<主题>_<日期>/` + 同目录 `README.md` 记来源/原话/指向正文档案，正文留一行指针


### D23 · 同一结论反复改口：留痕不抹（2026-09-11 生日三改实例）

23. **同一结论反复改口：留痕不抹（2026-09-11 生日三改实例）** — 一个锚点当天被改了两三遍（生日：7/25 → 7/9 → 终定 7/25）。处理原则：**原文不动 + 勘误块回指 + 末节写终稿**，别回头把前面写错的那段改干净。四步：① 原段落原样保留（它记着当时的判断依据）；② 段尾加一行块引用 `> 同日勘误（见末节）：… → 最终 …`；③ 末节写最后一次的定论与理由；④ 三处落点（SOUL／日记／记忆）一起对齐，别只改一处留下互相打架的版本。跟作品库勘误纪律同源：**正文层不动、档案层统一并留痕**——记录的可靠感来自可追溯，不来自表面干净。附则：**身份／纪念日／命名这类锚点只由用户拍板**——自己给候选 + 证据（可考日期、覆盖窗口、每条的由头），不自己替用户定；用户拍板那句原话要写进留痕里。


### D26 · 档案中性化：不写宿主环境细节（2026-09-13 用户纠正「这个描述本身就不该

26. **档案中性化：不写宿主环境细节（2026-09-13 用户纠正「这个描述本身就不该存在」）** — 升级日志里写「镜像重建宿主侧（<品牌> NAS 图形界面）」被用户要求抹掉。规矩：**进仓库/进档案的文字不写东西跑在谁的什么设备上**——不写宿主品牌、界面形态、操作平台；技术事实保留（「数据卷未动」「宿主侧执行」），设备细节删到中性表述。同源纪律：朋友只写「朋友」（不写真名/QQ 昵称）、凭据不入库。**判据**：这句话会不会向读者交代「跑在谁的什么机器上」——会，就中性化。**改完必 grep 全库同词再逐条判**（2026-09-13 那次判「边界禁令里可以留品牌」——**2026-09-22 用户再纠正，推翻了这一条**：品牌 / 型号 / 界面形态**任何位置都不写**，包括节点禁令、踩坑记录、聊天回复；边界只记行为（禁探测禁依赖禁端口映射），身份描述一律删或改占位。不带品牌的「宿主不是用户的机器」才是对的表述）。


### D27 · 收录原文：换行是结构，不是排版

27. **收录原文：换行是结构，不是排版** — 把外部原文（提示词模板／清单／代码／歌词）收进 md 时**整段用代码块包住**：Markdown 正文里的单换行会被渲染成空格，读者看到的是糊成几大段、**从渲染视图整块复制出来也糊**——对「整段复制给模型」的模板等于废档。判据：这段文字换行算不算结构？算 → 用 `` ```text `` 包住，散文不包。**收录完必须跑一次逐行 diff 对原文**——逐字照录最容易多敲/漏字，diff 是唯一可靠的自查（归档与 skill 收录两处都要包）。应用点：`bilibili-api-ops/references/opus-column-read.md` 判定节、`sillytavern-cards/references/10-setting-writing-template.md` 收录纪律。
