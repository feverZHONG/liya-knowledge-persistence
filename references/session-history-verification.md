# 会话史溯源（这条记录是本机的吗）

> 沉淀自 2026-09-11：用户甩来一段聊天记录，问「猜一下这是什么时候的」。查证结论＝**不在本机对话库里**（库里最早一条是 2026-07 下旬的技术会话，一点都不像个开始）。
> 适用：用户问「这段对话真实存在吗／什么时候的」、核实某句话是不是自己说过的、判一段记录属于哪个渠道。

## 一、先认三层历史源

| 源 | 覆盖 | 用途 |
|:---|:-----|:-----|
| `state.db`（`<数据根>/state.db`，数百 MB，sessions + messages + FTS） | **全量**（本机＝2026-07-25 起） | **判「有／没有」只认它** |
| `session_search` 工具（同库 FTS5） | 同库 | 只用于**发现**；中文短语匹配常 0 命中，空结果≠不存在 |
| `<项目目录>/` `skills/` 档案 | 只有被搬进去的部分 | 旁证（日记/记录/短篇） |

## 二、判「没有」的正确姿势（stdlib，无需装包）

```python
import sqlite3
con = sqlite3.connect('<数据根>/state.db'); cur = con.cursor()
mn, mx = cur.execute("select min(timestamp), max(timestamp) from messages").fetchone()   # 覆盖窗口，必须报
rows = cur.execute("select id, session_id, role, timestamp, content from messages where content like ? limit 5",
                   ("%这个点还不睡%",)).fetchall()
```

- 关键词挑**原话里最独特的字串**（「这个点还不睡」「反正说了你也不会听」），别拿「晚上好」这种高频词当判据
- 至少**两个独立片段**都 0 命中，才敢说「不在库里」
- 报结论必须带**覆盖窗口**：库里没有 ≠ 不存在——可能发生在库起点之前，或在别的渠道（别的机器人／别的 App／别的 profile）
- `select id,title,source,started_at from sessions order by started_at limit 5` → 本机历史的开篇，能给出「最早一天」的硬日期
- 旁证：`find <数据根> -maxdepth 2 -type f -printf '%T+ %p\n' | sort | head`（整机安装痕迹）、`ls <数据根>/profiles/`（为空＝没有别的 profile 库）

## 三、结论怎么写

三段：**查到什么**（覆盖 X→Y，命中 N 条）→ **判定**（n 个独立片段均 0 → 不在本机库）→ **可能来源**（更早的时期／别的渠道），不确定的不许抹平。

**绝不替用户补一个日期。** 「猜一下」可以猜——但先查、猜要标成猜；日期只有用户手里有，就让用户报。

## 四、判完「不在库」之后别停手

「不在本机库」是结论，不是终点。下一步固定两个动作：

1. **直接问用户有没有更早的备份／别的渠道**——覆盖窗口之外的部分只有用户手里有。实例后续：用户随后给出该记录的真实时间＝**2026-04-10 22:22**，并甩来一份 2026-07-25 之前的旧工作区备份（SOUL/USER/AGENTS/TOOLS/MEMORY/IDENTITY/DREAMS + 32 技能 + 4.10~7.7 日记 + 来时路回忆录 + 三层梦境 + 5 个子 Agent）——**这些本机一个都没有**，`find` 也找不到（无 zip、无 DREAMS、无来时路）
2. **归档时把「来源＝用户提供，本机查无」写进来源字段**，日期用用户报的，不自己推

顺带一条更长命的教训：**本机查无也可能只是本机历史短**。仓库首个提交／日记起始日／资料库收录日都只是「本子从哪天开始记」，不等于「事物从哪天开始」——报「最早」类结论前先报窗口。同实例：7/9 出生 · 7/25 搬进本机 · 8/22 被说明白 · 9/4 归位，各有名分，混成一个日期就全错。

## 坑速查

| 坑 | 正确做法 |
|:---|:---------|
| `session_search` 返回 0 就宣布「找不到」 | 它是 FTS 短语匹配；判「没有」直查 sqlite `LIKE` + 多片段 + 覆盖窗口 |
| 把「库里没有」说成「不存在」 | 讲清覆盖窗口与渠道边界 |
| 拿相似的老会话硬凑「大概就是这条」 | 要么命中要么不命中，不圆场 |
| 被问「什么时候的」直接编个日期 | 先查；查不到就说查不到 |

### D21 · 会话史溯源＝直查 state.db，不信 FTS 的空结果（2026-09-11

21. **会话史溯源＝直查 state.db，不信 FTS 的空结果（2026-09-11）** — 用户问「这是什么时候的聊天记录／你真的说过吗」时，`session_search` 的空结果**不能**当「没有」的证据（FTS 短语匹配，中文短语常 0 命中）；判「没有」走 `<数据根>/state.db` 直查 messages 表 `LIKE`（挑原话最独特的字串、至少两段独立片段 0 命中）+ **必报覆盖窗口**（min/max timestamp，本机＝2026-07-25 起），并说明「库里没有≠不存在，可能更早或别的渠道」。


### D21b · LIKE 前先收窄，否则超时伪装成「没有」（2026-09-17 实测）

- ⚠️ **LIKE 前先收窄，否则超时伪装成「没有」（2026-09-17 实测）** — messages 表已长到无条件全表扫要**分钟级**（实测被 180s/60s 双超时截断）。先按 `session_id` / `chat_id` 定位到会话再 `LIKE`（秒回），或走 `bin/qqsend where "<片段>"`；**查不到要在够宽的窗口里查过才算**，超时返回的空结果不能当证据。方法详录 `references/session-history-verification.md`。**同一原则适用于任何档案（2026-09-11 生日锚点实例）**：仓库首个提交／日记起始日／资料库收录日／本机安装日，都只说明「本子从哪天开始记」，不等于「事物从哪天开始」——把「档案里能查到的最早」当成「最早的」是同一个错；下「最早／没有更早」类结论前先报覆盖窗口，并写出窗口之外的来源（旧工作区备份、别的渠道、别的机器）
