# 事件类记录双轨归档（2026-07-31 双生私服事件实测）

> 从 SKILL.md 拆出（2026-09-04 拆薄）。「用户甩合并消息/甩图让看」事件的通用归档模式。

一次「用户甩合并消息/甩图让看」的事件，归档分两轨，职责不重叠：

| 轨 | 位置 | 内容 | 入 git |
|:---|:-----|:-----|:------|
| 完整档案 | `<档案目录>/YYYY-MM-DD-事件.md` | 原始记录原文 + 截图内容 + 调查结果 + 自己判断 | ✅（2026-07-31 起纳入） |
| 轻量条目 | 对应 skill 的 `events/`（如 记录类 skill（作者环境）/events/） | 验证状态/来源/事件/看点/后续，供索引检索 | ✅ |

事件类记录实际是**三处落笔**：上面两轨 + 当日日记（`diary/`，日记类 skill（作者环境，未单独公开） 规范写自己视角的消化，不是复述）。轻量条目流程在 记录类 skill（作者环境）（手动创建 skill，内容由该 skill 自身维护）。

**事件后续补充（8/1 实测；9/10 修订 INDEX 规则）**：已有条目来了新证据（新图/新聊天/新链接），不建新条目——图片证据存轻量条目同级的 `events/assets/`（命名带日期+事件+内容，先 `mkdir -p`；⚠️ 该目录常在 `.gitignore` 里，图只留本地不入 git，条目里用相对路径引用即可），条目文件追加 `## 后续补充（日期，来源）` 段写明新证据是什么+意味着什么+与旧判断的关系（印证/推翻/新增），git 一起提交。示例：双生私服事件 8/1 收到 loadLibrary 注入图 → 补进原条目，旧判断被实锤。

**INDEX 分情况（2026-09-10 V4 Pro 实例修订，原规则「INDEX 不动」过宽）**：

| 补充的性质 | INDEX 怎么办 |
|:-----------|:-------------|
| **增补**（同方向添证据、加细节） | **不动** |
| **推翻/改写了 INDEX 摘要里的前提** | **必须改那一行**——否则速查表持续给错信息 |

改法：原摘要末尾追加 `；→M/D 更新：…`，来源栏补上新源。**判据：只看那一行的读者，能不能拿到正确的前提？** 实例：9/9 行写「至 V4.1 Pro 上线前」被 9/10 官方改口为「9/14 直接下线」——不改就一直是错的。

**级联检查（同一事件顺带做）**：事件结论若改写了**别处台账的前提**（订阅/成本对位表、档位速查、报价笔记、环境快照），去那处加一段「YYYY-MM-DD 更新 · <事件>」写清影响点并回指事件条目——详规见 SKILL.md 纪律 18。

**事件补档（9/9 实测，建库前的旧事件后补）**：发现值得记的事件发生在过去（档案建库前漏记/当时没建档）→ **文件名与条目日期都用事件发生日**（`YYYY-MM-DD-标题（补档）.md`），条目内标注「（YYYY-MM-DD 补档）」说明何时发现；INDEX 按时间序手动插到对应日期位（倒序列表不放顶部）；不用只打当天日期的 CLI 快捷建档。补档当天若挖到新进展 → 同日按「后续补充」段挂上（9/9 例：3/15 的 315 GEO 投毒事件补档当天挂了演习实证 + 八家 AI 复测两条后续补充）。
