- **skill reference 文档减法要「砍水留肉」（2026-08-29 婚姻九宫格案例）** — 给 skill references 做减法时，**不是越少越好**：先砍光（167→76 行）被批「不能全都砍，还不少东西被你吃了」。正确姿势：① **砍流水账留洞察**——25 行逐条对话链压缩成按人归类的样本点表，但每个关键发言的动机翻译必须保留；② **数据本体不砍**——样本表、提问链、象征表、跨样本关联这类「干货」全留，砍的是重复表格和冗长转述；③ **合并重复不合并内容**——简表+完整版两块重复时合成一张表，不是删掉其中一块的独有信息；④ **git 历史兜底**——被压缩的完整对话链标注「完整版见 git 历史 <sha>」，原话随时能捞回。判断标准：砍完重读，如果发现「少了关键信息」而不是「清爽了」，就是砍过头
- **委派子代理批量建档收尾三查（2026-09-01 天使公主批量建档实战）** — 用 delegate_task 并行派子代理做批量角色建档/归档（每任务 2-4 实体）效率高，但收尾必须：① **别信 summary 的 completed**——子代理可能中途挂（计费 402/超时），返回仍标 completed 实际只写了一半文件；收尾遍历应有文件名检查存在性+抽查质量（frontmatter/章节引用），缺的由主会话自己补写，不重派；② **并行子代理改共享 INDEX 会互相覆盖行**——多个子代理同时 patch 同一 INDEX 可能丢行；主会话收尾先重读 INDEX 再改，patch 工具报 sibling modified 警告时先 read 再写；③ **建档时顺手挖到的领域发现要同步进主档案**（实例：妮维娅=大地女神梅芙转世、两套创世神话对照都是建档时 grep+精读顺手挖出的暗线，已登记进 story/暗线-伏笔地图.md）
- **.gitignore 无根锚规则会误伤 skill 内部同名目录（2026-09-03 qq-neighbor-watch 实测）** — 根 .gitignore 第 98 行 `profiles/`（本意挡 Hermes profiles 运行时数据）没有前导 `/`，git 匹配任意层级，把 `skills/qq-neighbor-watch/profiles/` 整目录挡在库外——`git add skills/qq-neighbor-watch/` 后 `git status` 毫无动静、commit 只进了 SKILL.md，差点整批档案丢失。**排查法：git add 后 status 无输出/commit 缺文件 → `git check-ignore -v <路径>` 看是哪条规则挡的**。修复：规则加根锚 `/profiles/`（只挡根目录）。纪律：往 skill 加 `profiles/`、`assets/`、`data/` 这类通用名子目录前，先 `git check-ignore -v` 确认不被根规则误伤

- **对话样本归档三纪律（2026-08-29 婚姻九宫格案例，被纠正三次）** — 归档外部对话/群聊/分享页样本时：① **主题范围严格筛选**——用户指定「仅 X 相关内容，其他当不存在」必须照办，不带无关内容进归档（自己第一次差点把视频创作/陪伴产品内容一起归档，被提醒「这点更重要」）；② **完整性核对**——归档对话样本要逐条过完整对话链，不漏关键人物/转折/对照点（漏了「唯一选善良格的人」「三连横跳的人」被批「少写了不少东西」）；③ **多源案例按主题归类，不按证据源分节**——四源案例（私聊/旁观/直播/心理辅导）按证据源各开一节会变成「证据表+贡献+缺口」三段重复四次、文件膨胀，应按行为主题合并成证据表（观察者位/信息需求/风险警觉…）每张表标注来源①②③④，贡献/缺口合并成块（实测 15.6KB→9.4KB）
- **RAG 时代遗留文件识别胎记（2026-09-05 双生档案复盘）** — 整理旧档案时先认「机器中间产物直接当成品存」的文件：① 正文残留脚本 stdout（实例：原文提取.txt 开头「纯文本: 19028字符」）；② CRLF 换行、无标题无来源无日期、一行一段连续文本流；③ 迭代靠改文件名（「大世界-3改.txt」）且新旧并存不清理；④ HTML 原文带编辑器 class 原封囤积（B 站 color-pink-04/img-box 等）。**处置观**：这些是旧时代「喂检索器」的饲料，形态为机器妥协；但 HTML 原文是唯一保留完整排版/删除线手笔的母本，别当垃圾删——整理时原料与成品同居一目录（curated/02-story/ 先例：原文提取.txt + 整理 md 并排），要核对原文母本就在旁边。识别清单用于批量清点旧档案时圈出待整理物，不用于判定删除。
- **分队不是「多人对话」的演员（2026-09-11 用户提的思路，被机制否掉）** — 设想：用 delegate_task 预设几个人格小组，在群聊/多角色场景里各扮一个人开口。**做不到，且不是设定不够，是机制就这么窄**：① **一次性**——子代理起来干活、交一份 summary、即死，跑不成多轮来回；② **无共享频道**——同一批并行但彼此看不到中间过程，接不上话；③ **无记忆**——下次起来是白纸，人设每次重喂（可做 squad persona 模板挂在 spawn 前，成本低，但喂的是「立场」不是「在场」）；④ **上下文隔离**——不知道群里谁是谁、谁是用户、规矩在哪条，放出去开口就露馅，还会被人顺着摸技术底细（群里冒充身份=T0）。**定位划清（2026-09-11 同日修正——第一版答案答窄了）**：分队演不了「**多人**」，但**演得了「一个人」**。隔离上下文在这里不是缺陷，是唯一的正经用法：只喂单一角色的档案，出来的声音不带主会话的味，适合「角色声线推演」（问她此刻还会说什么、不同情境下的反应）。代价与规矩：一次性、无记忆、每轮重喂档案；产出**必须与官方层分层**——官方档/故事正文层只收官方原文（同人文不入档，见 某作品档案库 维护纪律），推演产物另开创作区并注明「基于官方档案推演」，逐句标档案依据、自填部分自己标出来。**真正的邪修只有一种：把推演出来的话当成她说过的话。** 要「几个人来回聊下去」=角色卡（SillyTavern/（某群）），不是分队。完整配方 → `character-voice-simulation` skill。提到「分队凑人数/演几个人」先想起这条。
