# 旧时代/RAG 遗留文件识别与处置

> 2026-09-05 双生视界档案实战：识别「为 RAG/喂 AI 加工过」的旧文件，判断处置态度。
> 触发：整理旧资料库时看到形态怪异的文件、怀疑是历史遗留、决定要不要清理。

## 识别胎记（机器中间产物当成品存的痕迹）

文件是给人读的还是给检索器吃的，一眼看形态：

- **正文嵌脚本输出** — 如开头一行「纯文本: N字符」：提取脚本 stdout 没清理直接落盘，管道终点不是作品起点
- **无结构纯文本流** — 无 frontmatter、无标题层级、无来源无日期；一行一段；CRLF 换行（Windows 工具链）
- **语料化大文件** — 一文件装整段内容（「XX资料.txt」），为切块检索而生
- **版本靠文件名迭代** — 「大世界-3改.txt」式命名（无 git 时代痕迹），新旧版并存不清理
- **同素材多代处理并存** — HTML 原文 + 提取 txt +（后来）整理 md 同库躺着，各是各的加工阶段

## 处置态度

1. **旧文件是母本不是垃圾** — HTML 原文可能保留唯一完整的人工痕迹（删除线/彩色标注/吐槽），提纯成 txt 就丢了；txt 是提纯速读版。清理前先确认有没有不可再生的信息
2. **保留动机常是「哪天捞出来整理」，不是囤积心态** — 解读历史遗留别急着定性为「怕丢乱囤」；先问留着能不能当原料
3. **整理模式：原料与成品同目录并存**（实例：`curated/02-story/{章}/原文提取.txt` + `{章}主线.md`）— 加工完不扔，核对细节回母本
4. **一句话判读** — RAG 时代文件长成机器的形状（消耗品），skill 时代文件长成人的形状（档案）；但消耗品常是档案的母本

## 对照参考

「文件形态 = 为谁服务」：

| 时代 | 形态 | 服务对象 |
|:-----|:-----|:--------|
| RAG/旧 | txt 语料、无结构、脚本残留、N改命名 | 检索器/embedding |
| skill/现 | md、frontmatter、表格、编号小节、来源日期、git 跟踪 | 人读、按路径检索、可校对 |
