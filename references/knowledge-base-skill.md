# 知识库型 Skill 模式

> 2026-07-31 与用户确认的思路：skill 可以做知识库。
> 核心：SKILL.md 当导视索引，数据本体放 skill 内部目录，按需加载。

## 一句话

**skill 天生就是知识库容器**——SKILL.md 薄入口 + 数据文件按需加载。不是要不要做，是怎么组织。

## 现有范例

| skill | 形态 |
|-------|------|
| `角色资料库` | 纯数据本体（characters/story/setting/sources 129份）+ references 索引 |
| `internet-memes-reference` | 分类目录（memes/流行梗|语言陷阱|技术梗）+ 导视表 + 模板 `_template.md` |
| `gbf-relink` | references/skill-data/ 几十个因子数据 md，按名检索 |
| `（私档）-crusaders` | 全系列档案 |
| `某连载 skill` | 已发布稿件 P0/P1 拆分 |

## 为什么用 skill 而不是普通文件

| 对比 | skill | workspace 文件 |
|------|-------|----------------|
| 检索 | 按语义加载，skill_view 读哪份给哪份 | 死的，要靠人记得路径 |
| 上下文 | 只加载被需要的文件 | 全量读才看得到 |
| git | 跟仓库走 | 可能被 gitignore 或散落 |
| 触发 | description 在系统提示里，遇到场景自动想起来 | 没有入口 |

结论：**知识类、长期复用、要 git 跟踪的 → skill；单次审计、临时记录 → 文件。**

## 知识库型 skill 的标准结构

```
knowledge-base-name/
├── SKILL.md          ← 导视：目录结构 + 资料清单表 + 检索方式
├── references/       ← 索引规范（ARCHIVE-INDEX.md / ROSTER.md 等）
├── _template.md      ← 条目模板（新增数据时复制填空）
└── <data-dirs>/      ← 数据本体，按类分目录
```

要点：
1. **SKILL.md 是导视不是正文**——列目录结构、资料清单（目录+内容+文件数）、检索方式。数据放子目录。
2. **数据本体与索引分离**——数据目录只管存，references/ 管怎么找（符合做减法哲学：入口薄，内容分片）。
3. **模板驱动新增**——`_template.md` 保证每条数据格式统一。
4. **目录按类分**——不是按时间（时间分片是 archive-pattern 的活），知识库按主题类目分。

## 与归档目录模式（archive-pattern.md）的分工

| | archive-pattern | 知识库型 skill |
|--|----------------|----------------|
| 用途 | 长期积累同类数据（存档文章/日志/下载） | 组织已成体系的知识（设定/梗/攻略） |
| 目录 | 按年/月时间分片 | 按主题类目分 |
| 归属 | 常在工作区/数据目录 | 在 skills/ 下 |
| 索引 | INDEX.md 时间序 + SOURCES.md 分类序 | SKILL.md 导视表 + references 索引 |

一句话：**归档是流水账，知识库是分类架。** 按时间积累的叫归档，按主题组织的叫知识库。

## 什么时候把一个 skill 升级成知识库

- 数据项多到 SKILL.md 装不下（10+ 条目）
- 内容有明确分类维度（角色/版本/类目）
- 会反复按名检索某份资料
- 新增条目有固定格式

## 建库范围先对齐（开档决策，2026-09-03 history-archive 实战）

> 实例：victory-day-parade（九三阅兵档案）建完当天被用户要求改名 history-archive（通用历史档案库）——首版把范围定窄在单事件。

- **名字范围先问清**：事件级（九三阅兵）/ 主题级（抗战胜利纪念）/ 通用库（历史档案总库，事件只是首档）——三个宽度差别大，目录结构与扩展约定跟着变。拿不准先 clarify，别等建完再改名
- **资料组织方向先对齐**：同一份素材，「记录向」（流程/装备细节堆叠）与「历史向」（为什么重要+意义主体，细节降附录）是两种档案。开档先问「给什么用」——用户说「给历史用」就是要脉络+意义为主、细节作附录
- **通用库开档就立规矩**：「扩展约定」（新主题怎么加）+「防膨胀内建」（下节七规）随库一起建，别等第二个主题进来再补

## 防膨胀内建（知识库开档即立，2026-09-03 自 history-archive 沉淀）

> 知识库/资料库型 skill 会一直长。规矩开档就立，别等臃肿再砍。
> 实例：history-archive（九三·抗战胜利纪念首档）开档时内建七规，当场清掉两处重复。

1. **结构即减法** — SKILL.md 永远是导视（触发+结构表+库级速查），正文归 references/数据目录。新条目只许加在数据层，不许写进 SKILL.md
2. **必留清单（砍之前先列）** — 每类档案四类必留：日期/沿革、官方定性或源口径、核心事实、意义。二手解读、重复叙事、装饰细节可砍
3. **内容只讲一遍** — 同一件事不跨文件重复讲。概念/意义档与事件/实例档分工，交叉处一句带过 + 指文件
4. **时效标注** — 名单/数字/状态标采集时间（截至 YYYY-MM）；过期细节不冒充现状；更新覆盖旧值不堆新层
5. **收录门槛** — 只收验证过的事实；单源线索标「待核」不硬写；新资料先对照必留清单，不加重复段
6. **精简触发** — 单档明显膨胀 / 被说「厚」/ SKILL.md 库级内容超一屏 → 跑一轮减法
7. **砍了留痕** — git log 是砍伐记录；大砍前先列必留清单（规则 2），对照再动手

配套纪律：七规在具体库里落地时允许按库型改写表述（如档案库把「收录门槛」写成「只收官方口径+多源验证」），但**别删条目类别**——每类防的是不同的病：1 防入口膨胀，2 防砍过头，3 防重复叙事，4 防过期冒充现状，5 防堆料，6 防拖延，7 防砍了白砍。

## 导视拆 INDEX（2026-08-31 internet-memes-reference 实战）（2026-09-22 从 SKILL.md 拆出，内容一条未删，逐字搬运）

知识库型 skill 的 SKILL.md 导视/索引表是最大重复块——**导视表拆到 skill 根独立 `INDEX.md`**：① 先做脚本依赖分析（脚本读写导视？拆只改路径常量）；② 建 INDEX.md（数据原样搬，脚本依赖结构保留）；③ SKILL.md 换一行指引；④ 搜全库引用同步；⑤ 实测验证。**装饰 emoji 端走（用户拍板）**：类目标题/流程步骤 emoji 是噪音一并清，有识别作用的字段 emoji 可留。
